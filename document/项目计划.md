## 📋 **技术选型详解**

### **前端栈（为什么选 Next.js 14）**

**Next.js 14 App Router**：
- ✅ **完全服务端渲染 (SSR)** → 商品详情页、分类页 SEO 友好
- ✅ **静态生成 (SSG)** → 热门商品页缓存 24h，减服务器压力
- ✅ **增量静态再生成 (ISR)** → 价格更新后自动刷新缓存，不需要全量重建
- ✅ **API 路由内置** → 支付 Webhook、上传接口直接写在 `/app/api/` 目录
- ✅ **图片优化** → `next/image` 自动 WebP 转换、尺寸压缩

**为什么比 Remix/Astro 更好**：
- 对奢侈品电商来说，组件复用度高（商品卡、购物车、支付表单）→ React 生态最成熟
- 全栈开发（前后端在同一项目）→ 迭代快

**UI 框架：Tailwind + shadcn/ui**：
- Tailwind：快速开发、响应式天然支持
- shadcn/ui：奢侈品风的组件库（按钮、模态框都有品质感）
- 替代方案：Headless UI + 自己设计 ❌（太耗时）

**状态管理：Zustand 而非 Redux**：
- Redux：太重（购物车 + 用户状态 + 支付流程不需要那么复杂）
- Zustand：~2KB、API 简洁、DevTools 支持好

**数据同步：TanStack Query（React Query）**：
- 自动缓存、重试、后台更新
- 解决的问题：用户打开商品详情 → 网络抖动 → 自动重新获取最新价格
- 支付后自动刷新订单状态

**动画：Framer Motion**：
- 专为 React 设计
- 高端感关键（图片滑动、加载动画、确认弹窗）
- 性能好（60fps）

### **后端栈选择**

**方案 A：Node.js + Hono（推荐）**
```
优势：
- 与 Next.js 同语言生态（TypeScript 一套用）
- 轻量快速（比 Express 快 3 倍）
- 可直接部署在 Vercel 的 Edge Runtime
- 支付 Webhook 验证签名逻辑最快实现

缺点：
- CPU 密集业务不优（推荐算法等）
```

**方案 B：Python + FastAPI（如果有复杂算法）**
```
优势：
- 数据科学库丰富（numpy/pandas 用于价格趋势分析）
- 推荐算法实现快（scikit-learn）
- 异步原生支持（async/await）

缺点：
- Node.js 下沉到另一个服务 → 运维复杂度 +1
```

**我的建议**：
- **初期（MVP）**：用 Node.js + Hono，全部部署在 Vercel
- **后期（2-3 个月后）**：如需要复杂推荐算法，分离出 Python 微服务（可用 Celery）

### **数据库选型**

**PostgreSQL（主库）**：
- ✅ JSONB 类型 → 存储商品属性（材质、尺寸、颜色等变量）
- ✅ 全文搜索 → 搜索商品名、品牌
- ✅ 事务隔离 → 支付时库存锁定（防止超售）
- ✅ 行级安全 (RLS) → 用户只能看到自己的订单

**Redis（缓存 + 会话）**：
- 热门商品缓存（价格、库存）
- 搜索结果缓存
- 用户会话（登录状态）
- 购物车（临时存储，下单时转入 DB）
- 库存预锁定（秒杀场景）

**选型理由**：
- PostgreSQL 对标 MySQL，但 JSON 支持更好
- 无需 MongoDB（关系型数据够用，奢侈品属性虽多但结构化）

---

### **文件存储**

**Cloudflare R2**（推荐）vs S3：
| 方案 | 成本 | 速度 | 功能 |
|-----|------|------|------|
| **Cloudflare R2** | $0.015/GB（便宜 80%） | 全球 CDN 一体 | 图片优化、自定义域名 |
| **S3** | $0.023/GB | 需配 CloudFront 单独付费 | 功能全、文档多 |

**我的建议**：用 R2 + Cloudflare 图片优化（自动 WebP、尺寸裁剪）。

**上传流程**：
1. 前端调用后端 API `/api/upload/presigned-url`
2. 后端生成 presigned URL（有效期 15 分钟）
3. 前端直接上传到 R2（不经过你的服务器）
4. R2 上传成功后回调前端
5. 前端保存图片 URL 到数据库

**好处**：上传不走服务器 → 减轻负担、支持断点续传

## 💳 **支付系统集成（关键）**

基于前面的讨论，支付系统这样做：

```
Next.js API 路由：
/app/api/payment/create-order     → 生成订单、调用决済代行 API
/app/api/payment/webhook          → 接收支付结果、更新订单状态
/app/api/payment/status           → 前端轮询订单状态

工作流：
1. 前端：用户选择支付方式
2. API 路由 /create-order：
   ├─ 创建订单（DB 插入）
   ├─ 调用决済代行 API（GMO-PG）获取支付链接/二维码
   └─ 返回支付 URL 给前端
3. 前端：重定向到支付 URL（或显示二维码）
4. 决済代行处理支付
5. Webhook /payment/webhook：
   ├─ 验证签名
   ├─ 更新订单状态为「已支付」
   ├─ 库存扣减
   └─ 发送确认邮件
6. 前端：轮询 /payment/status，支付成功后跳转到订单详情
```

## 🏪 **奢侈品特殊功能架构**

### **1. 产品鉴定 & 回收报价流程**

```
用户上传二手商品：
1. 用户上传 3-5 张照片 + 填写状态（品相、使用年限）
2. 上传到 R2，生成缩略图
3. 后端存储商品信息（pending 状态）
4. 通知"鉴定师"后台有新商品
5. 鉴定师查看照片、填写真伪判断、定价
6. 系统生成报价单，发邮件给用户
7. 用户同意报价 → 生成快递单 → 用户寄出
8. 鉴定师收货、复检、确认支付
```

**数据库设计**：
```sql
CREATE TABLE resale_items (
  id UUID PRIMARY KEY,
  seller_id UUID REFERENCES users,
  brand VARCHAR,
  category VARCHAR,
  condition VARCHAR,  -- excellent / good / fair / poor
  images JSONB,  -- 存储图片 URL 数组
  status VARCHAR,  -- uploaded / pending_appraisal / appraised / accepted / shipped / completed
  appraiser_id UUID REFERENCES staff,
  appraised_price DECIMAL,
  appraised_at TIMESTAMP,
  created_at TIMESTAMP
);
```

### **2. 搜索和过滤**

PostgreSQL 全文搜索 + 多维过滤：
```sql
SELECT * FROM products
WHERE 
  to_tsvector('japanese', name || ' ' || brand) @@ plainto_tsquery('japanese', '🔍查询词')
  AND price BETWEEN min_price AND max_price
  AND category = '包包'
  AND condition IN ('excellent', 'good')
  AND stock > 0
ORDER BY relevance DESC, price ASC;
```

**前端实现**：
- 多选过滤器（品牌、类别、价格区间、成色）
- 即时搜索（防抖，每次输入 0.3 秒后调用）
- 结果分页（每页 20 件）

### **3. 价格追踪 & 推荐**

```
后端定时任务（每日 0 点）：
1. 统计各品牌、各类别的价格变化
2. 用户关注商品价格下降 → 发邮件通知
3. 用户浏览过某品牌 → 推荐相似商品

实现：
- Cron job 脚本（node-cron）
- 或用消息队列（Bull/BullMQ）
```

## 🎯 **最后建议**

1. **前端框架不要改** → Next.js 14 是业界标准，你看竞争对手也用
2. **后端选 Node.js** → 一套 TypeScript 团队好管理，Vercel 部署无缝
3. **数据库选 PostgreSQL** → 不要用 MongoDB（关系型数据更安全，尤其支付)
4. **支付系统关键** → 早期集成微信+支付宝，是你相对竞争对手的差异点
5. **回收流程是核心竞争力** → 后面优先打磨鉴定流程、用户信任

你现在要决定的是：**自己部署 vs 用托管平台**？

- **Vercel + Supabase**：快、省心、但灵活性受限、账单可能贵（流量大时）
- **自建 VPS（AWS/DigitalOcean）**：便宜、完全控制、但要自己运维

给你的建议：**初期用 Vercel + Supabase，业务稳定后迁到 AWS**。
